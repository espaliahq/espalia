# Assessments — Stimulus Controllers

> Part of the [assessments.md](../assessments.md) guide set. Read this when: changing or adding a Stimulus controller the assessment screens use.

## Stimulus controllers

| Controller | Responsibility |
|---|---|
| `matrix_controller.js` | Chip-click focus and the single-card swap (`#loadCard`), card-header click focus (capability), scroll-driven capability focus via IntersectionObserver, smooth-scroll-under-sticky-headers, URL sync (`?capability=` + `?level_ordinal=` for focus; accumulating `levels[<stable_id>]` map for per-capability rendered level), URL-first focus restoration on connect, `data-focused` stamping on cards, sibling card dimming when a card is URL-focused. Shared with the framework explorer (table-mode methods live there). |
| `category_nav_controller.js` | Publishes `--sticky-header-h` via `getBoundingClientRect().height` + `Math.ceil` + `ResizeObserver`. Smooth-scrolls to category sections on chip click. Updates the active chip on scroll (suppressed for 900ms after a chip click — see [*Category navigation*](../assessments.md)). |
| `assessment_sync_controller.js` | ActionCable sync, self-submit suppression window, dual-frame reload, focus-param and lens-param (`as_role` / `as_level`) merge before reload. Also reloads each root-mounted dialog's content frame (`dialogFrame` targets, from their `data-reload-src`), so an open dialog shows someone else's rating without closing. |
| `comments_thread_controller.js` | A comment thread: the composer toggle, inline edit and reply forms, Cmd/Ctrl+Enter submit, the "↳ replying to" jump, and clearing the composer after a post. On a cell thread it also places focus after the response swaps the thread ([#625](https://github.com/mr-yum/growth-os/issues/625)): `releaseFocus` blurs a focused element with an id in the thread at `turbo:submit-start`, so Turbo's own focus restore can't take it back, and the new thread's `connect()` focuses what its `focus` value names (the viewer's own new or edited comment, or the add button after a delete) without scrolling, giving a row `tabindex="-1"` only then. See [*Level strip*](../assessments.md). |
| `lens_picker_controller.js` | The "Another role…" dialog: rebuilds the level select from the chosen role's levels, keeping the reader's ordinal (nearest, lower on a tie — the same rule as `Assessments::Lens`). |
| `activity_feed_controller.js` | Listens for `matrix:focus-changed` and narrows entries by capability + level focus. An entry about another role (`data-lens-href`) switches the page to that lens when its card isn't on the page. |
| `activity_pane_controller.js` | Opens and closes the activity sidebar (inline on lg+, a fixed overlay below), with its cookie and `?activity=` URL state. With `fitViewport` (both assessment show views) it caps the pane's height on lg+ at the room below the pane's own top, re-measured on scroll, resize and body resize, so the feed's last entries stay on screen — see Hard-Won Lesson 19. |
| `context_pane_controller.js` (shared with framework explorer) | Right-pane suggestion / activity panel state, URL focus sync. |
| `continue_assessing_controller.js` | Bottom-line CTA — dispatches a window event with the next-unrated capability stable_id + level, picked up by `matrix_controller#focusUnrated`. With `focusCard` (the capability map's spokes and lanes) the matrix also moves focus to the card. |
| `capability_map_controller.js` | Lights a capability's spoke and its lane together in the capability map, on hover and focus, by the `data-capability-map-key` they share. Its `zoom` action reloads the map's content frame at another level (`params.zoom`), and each render's `view` target keeps the zoom on the frame's reload source. |
| `dialog_refresh_controller.js` | Keeps focus in an open root-mounted dialog when a rating stream or a sync reload re-renders its content frame: finds whatever had focus again by `data-refresh-focus` or its id. |
| `modal_controller.js` | Generic `Kit::Modal` controller — open/close, body-scroll-lock. **Outside-click dismissal is opt-in** (`dismissOnOutsideClick` value, default off) so a stray background click can't discard a half-filled transactional form — modals close via the × button, Cancel, Esc, or a successful submit. **Esc routes through `modal#escape`**: an overlay opting in via `data-modal-dirty-guard="<message>"` confirms before an Esc discards typed input (audit issue #315 — the evidence and request-evidence overlays opt in); × and Cancel stay immediate as explicit dismissals. **Keyboard focus follows the APG dialog contract** (audit issue #317): on open, focus moves into the dialog — the panel (`tabindex="-1"`) while a lazy frame loads, then the first field on `turbo:frame-load`; Tab/Shift+Tab wrap within the open overlay; on close, focus returns to the invoker, falling back to the ancestor dropdown's kebab when the invoking menu item is hidden. Hosts the Delegates modal (standalone) and the unified evidence modal (embedded — a lazy `#evidence-modal` frame). |
| `submit_guard_controller.js` | Keeps one user action to one request (audit issue #335) by blocking a **re-entrant submit** — and nothing else. Mounted on a Turbo form, it flips a flag on `turbo:submit-start` / `turbo:submit-end` and stops any `submit` fired in between, on the form, ahead of Turbo's document-level listener — so a programmatic `requestSubmit()` can't slip past the disabled button. The in-flight *treatment* is Turbo's own: `config.forms.submitter` (default `"disabled"`) disables the submitter and `data-turbo-submits-with="Saving…"` swaps its label, both restored on `requestFinished` whatever the outcome (a validation error keeps the modal open for another attempt). Hand-rolling those here leaked a pinned `min-width` and stuck the label on a same-task double submit. Known edge: two submits in the same task both precede `turbo:submit-start`, so the guard arms from the second task onward — Turbo's navigator aborts the first submission there, so one request still lands. Mounted on the evidence modal form **and the request-evidence send form** — that one matters more: `Operations::Assessments::RequestEvidence` mints a fresh `request_id` per POST, so unlike the idempotency-harmless evidence save, a second submission that lands creates duplicate requests and duplicate notifications for every recipient. |
| `submit_fallback_controller.js` | Surfaces transport-level Turbo submit failures that are otherwise silent (audit issue #316). Claims non-stream error responses at `turbo:before-fetch-response` (form submissions only — frame-load failures belong to `frame-error`) so a 5xx HTML body is never rendered as the page, and injects a retryable message into a pre-existing `role="alert"` region (`Shared::SubmitFallbackMessage`) — connection copy for transport/5xx, reload copy for 4xx rejections. Domain errors (turbo-stream responses) stay with the server's own rendering. Mounted on the rating pill wrapper, the evidence modal panel, and the request-evidence modal panel — in each case the live region sits OUTSIDE the lazy frame, so it survives a frame swap. |
| `frame_error_controller.js` | Gives a **lazy turbo-frame's failed load** a voice (audit issues #328 / #365) — one instance per frame, mounted on an element wrapping that frame and its `Shared::FrameLoadError` block. **Mounting is a bare `data-controller="frame-error"` plus the two targets**: the five listeners bind themselves in `connect()` and unbind in `disconnect()`, rather than being declared as a hand-copied `data-action` string per site where one missed line would silently drop one failure shape. Three failure shapes, all verified against turbo-rails 2.0.23: `turbo:fetch-request-error` (network dropped), `turbo:frame-missing` (a response with no matching frame — **cancelled**, since its default renders Turbo's own "Content missing" into the frame and then throws; it does NOT navigate), and `turbo:before-fetch-response` → `responseReceived` (`FetchResponse#responseHTML` resolves undefined for a non-HTML body, so `loadResponse` renders nothing and dispatches *nothing* — e.g. a proxy's text/plain 502). `#failLoad` hides the frame (taking its stuck "Loading…" down with it), reveals the error block and moves focus into it; `retry` re-fetches by clearing `complete`/`src` and reassigning — no `loading` flip, since `#hasBeenLoaded` is set after the first attempt whatever its outcome and `sourceURLChanged` then fetches regardless of visibility. The retry URL comes from `turbo:before-fetch-request` (whose detail carries the genuinely-requested URL, immune to Turbo rewriting `src` to a redirected GET's final URL — a session expiry would otherwise pin every retry to the sign-in page), so **whichever controller points the frame needs no cooperation**; that same handler clears a stale failure the moment the next fetch starts. `loadSucceeded` un-hides the frame. **Loads only, never a form submitted inside the frame.** The two fetch events discriminate themselves — a `FormSubmission`'s `FetchRequest` carries the FORM as its target, so gating every handler on `event.target === frameTarget` excludes them (along with nested frames) — but `turbo:frame-missing` does **not**: Turbo dispatches it on `this.element`, the FRAME, unconditionally, including from `formSubmissionFailedWithResponse` → `loadResponse`. So frame-missing is claimed only while **armed**: `requestStarted` (which only fires for frame-targeted GETs) sets the flag and a load's end clears it. Unarmed, the event falls through untouched to Turbo's default — otherwise a 500 or auth bounce on an in-frame row save hid the whole editor/thread, along with the user's other typed edits, behind "Couldn't load…" whose Retry then re-GETs over that work. `connect()` likewise resets a failure state restored from a snapshot (fresh instance, no `requestedUrl`, and a hidden lazy frame can never re-fetch — permanently dead otherwise). Mounted on: the evidence modal panel, the request-evidence modal panel, each evidence card's discussion disclosure, and the explorer's binding-/level-editor modal bodies. |
| `evidence_modal_controller.js` | Drives the **unified evidence modal** (one modal for new/edit/respond, both surfaces). The page instance's `load` sets the lazy `#evidence-modal` frame `src` from a trigger's action params (mode + ids + entry cell + `return_to`), so the server renders the right form each open; the frame's *failure* state belongs to `frame-error` alongside it on the panel. The in-frame instance toggles the custom-type label and manages the "Applies to" link rows (each showing that cell's behavioural expectation + collapsible examples, read from an embedded JSON map) with the last-row remove lock. Replaced the old `evidence_form` / `evidence_edit_form` / `evidence_link_form` / `evidence_response` controllers. |

There is **no** `sticky_hero_controller.js`. The hero's collapse is pure CSS scroll-driven animation. See [*Hero Summary — Collapse on scroll*](scoring.md).
